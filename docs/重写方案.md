# R_N 资料库 · 重写方案（v2）

> 目标不是换技术栈，而是把「三个月里踩过的坑」变成结构上不再可能犯的错。
> 本文是评审稿：先说清楚哪一层要重写、为什么，再给可回滚的分阶段路线。
> 看完后需你拍板的四件事在最后一节。

---

## 一、现状诊断：五次真实事故，五个结构性缺陷

| 事故 | 表面原因 | 结构缺陷 |
|---|---|---|
| 站点显示「0 份文档」，数据明明都在 | 入库没写 `visibility`，读接口按 `'public'` 过滤 | **没有文档模型**：字段靠各处手写，缺一个字段 = 静默改变行为 |
| 索引空了没人知道，文档照样「入库成功」 | `applyDocChange` 抛错被吞进 `indexError` | **派生数据被当成真相**：索引与清单靠就地改，坏了没有自检 |
| 连删两份，只删掉一份 | 读-改-写碰上 Blobs 最终一致 | **写路径分散**：四处各自读改写，没有单一闸门与并发控制 |
| 307 页的书 502，库里留下半份 | 整本 49 万字进倒排索引，撞 26 秒上限 | **没有容量契约**：限额没写进设计，只在事故里发现 |
| 改了代码以为线上是新的，白排查半小时 | 函数里没有构建信息 | **部署不可观测** |

一句话：**当前实现把「真相」「派生」「缓存」混在一层，靠调用方自觉维持一致。**
重写的核心就三件事：**唯一真相 + 可重建派生 + 单一写入门闸。**

---

## 二、目标与不变式

四条不变式，实现全部围绕它们，测试也照它们写：

1. **单一真相**：`doc`（元数据）+ `text`（正文）+ `file`（原件）是唯一的真相；
   索引、清单、标签统计、分类计数全是派生物，随时可整份丢掉重建。
2. **写入即可见**：任何写操作返回成功之后，该文档一定出现在列表里。
   索引允许滞后，但滞后必须是**显式状态**（`indexPending: true`），不是"消失"。
3. **删除可恢复**：删文档先落墓碑（`deletedAt`），清理正文与原件是**后续步骤**；
   任何一步崩掉，`doctor --fix` 都能收尾。
4. **重建幂等**：`rebuild` 跑一次和跑十次结果一样，且只依赖真相层。

## 三、数据模型 v2

### 3.1 身份：稳定 ID 与内容哈希分离

现在 `id = sha256(内容).slice(0,12)`，于是「编辑」= 换身份，「重传」= 新文档。
改成：

| 字段 | 含义 | 用途 |
|---|---|---|
| `docId` | 由 `sourceKey` 派生的稳定 id（12 位 base32） | URL、外键、一切引用 |
| `sourceKey` | 归一化来源：`upload://资料/x.pdf` 或绝对路径 / 手动创建 | 同步与去重的**唯一键** |
| `contentHash` | sha256（全文） | 「内容是否变了」，不参与身份 |

好处：改一个标点不再换 URL；重复上传变成「同一份文档的新版本」；
外部站点（`01-smart-workstation`、`01-personal-blog`）引用的链接长期有效。

> 迁移期保留 `idAlias` 表（旧内容哈希 id → 新 docId），`/docs/{old}` 302 到新地址，半年后删。

### 3.2 字段与默认值

每个字段都必须有**显式默认值**，由唯一的构造函数 `normalizeDoc()` 施加：

```js
// _lib/doc-model.mjs
export const SCHEMA_VERSION = 2

export function normalizeDoc(raw, ctx) {
  return {
    schemaVersion: SCHEMA_VERSION,
    docId, sourceKey, contentHash,
    rev,                       // 每次写入 +1，乐观锁用
    status: 'active',          // active | archived | deleted
    visibility: 'private',     // ★ 已定：新建默认私有（见下）
    title, originalName, ext, type, mime, size, pages,
    folderId,                  // 所属文件夹（虚拟树里的一层）
    tags: [],                  // 自由标记（人给的 + 少量自动建议）
    summary, author, docCreatedAt,
    text: { chars, truncated, pagesExtracted },   // 正文抽取的**结果描述**
    preview: { kind, note },
    index: { rev, pending, error },               // 索引进度（不再是旁路 indexError）
    classify: { source, confidence, evidence },   // 可解释
    needsReview: false,
    createdAt, updatedAt,
  }
}
```

要点：
- `visibility`、`needsReview` 这类"行为开关"由构造函数强制给值，**缺字段不可能再发生**。
- **已定：新文档默认 `private`**。现有的 60 份保持 `public` 不变（迁移只补字段、不动值）。
  配套 UX 必须跟上，否则就变成我们自己制造的「传上去却看不到」：
  · 列表项显示锁标记；未登录视图明确写「访客视图：只显示公开文档」
  · 上传完成后给出「已存入（私有）—— 设为公开？」一键操作
  · 文件夹可以整层「设为公开 / 设为私有」，子项继承
  · 公开 API 也受同一规则：外部站点要读私有文档必须带 `read` 角色令牌，
    且**不能把令牌塞进静态页面**（要在对端函数的环境变量里）
- `index` 从旁路的 `indexError` 字符串变成结构化状态：UI 能显示「索引待更新」，`doctor` 能扫出来。
- `classify.evidence` 保留判定依据（哪条规则、哪个目录、哪个词、AI 哪段引用）——标签可解释了，复核才有意义。

### 3.3 墓碑与版本

- 删除 = `status:'deleted'` + `deletedAt`，索引摘除，正文/原件保留 7 天后由 `doctor --purge` 清。
- 内容编辑 = 新 `rev`；`PUT /docs/{id}/content` 的 409 语义沿用，扩展为 `If-Match: rev`。
- 同名不同版本：同 `sourceKey`、不同 `contentHash` → 保留 `history[]`（最多 5 版，只存元数据 + 指针）。

## 四、存储三层

```
真相层   doc-meta/{docId}        规范化后的 doc（唯一可写）
         doc-text/{docId}        正文分页
         doc-files/{docId}.{ext} 原件
             ↑ 只写这里，其余都能重建

派生层   doc-index/manifest      列表快照 { rev, builtAt, itemCount }
         doc-index/tags          标签统计
         doc-index/collections   集合/体裁/主题计数

检索层   doc-index/shard-000…127 倒排分片（BM25）
         doc-index/meta          词条数、平均长度、version
```

规则：

1. **列表读派生层，但派生层带 `rev`**。`manifest.rev` 落后于真相层的最大 `rev` 时，
   响应头带 `X-Index-Stale: true`，UI 显示一个小提示并提供「重建」按钮（复用现有 `/index/repair`）。
2. **索引不再读 `manifest` 推旧词频**。旧词频一律从该文档自己的 `text` 算 ——
   这正是索引孤儿事故的根因（拿别人的派生数据当基准）。
3. **删/改的顺序固定**：落墓碑 → 摘索引 → 删正文 → 删原件 → 清墓碑。
   每一步单独可重入，`doctor --fix` 按此顺序补齐。

## 五、分类与标签 v2（重点）

### 5.1 现在为什么不行

一条轴上同时塞了三件事，谁都不够用：

- **体裁**（这是习题、论文还是一本书）
- **主题**（讲继承、讲网络安全）
- **归档位置**（我的 Java 课程资料）

结果：60 份文档里 58 份判成「学习资料」，等于没分类；
标签被当成「关键词命中」，于是「物理」「英语」这种正文里撞词的东西也成了标签，
一份 39 页的编码规范拿了 8 个标签，其中一半和它无关。
而真正有用的信号（目录名 `L30_面向对象进阶/继承测试`）只被塞进标题里当弱提示。

### 5.2 三个轴就够了（原方案的四轴按「资料很简单」收窄）

| 轴 | 数量 | 来源 | 取值方式 | 例 |
|---|---|---|---|---|
| **文件夹** | 每份 1 | 你手动建 + 上传目录自动建 | 虚拟树，可改名/移动 | `Java 学习/L30_面向对象进阶` |
| `docType` 体裁 | 每份 1 | 结构信号（高精度） | 单标签 | 课堂练习 / 代码示例 / 电子书 / 论文 / 编码规范 / 合同 / 票据 |
| `tags` 标签 | 每份 0–5 | 受控词表 + 证据打分，可手改 | 多标签，带来源 | Java / 面向对象 / 继承 / 多态 |

原来的 `collection`（集合）与 `topics`（主题）取消，理由：
- 集合就是**文件夹** —— 文件夹现在是第一类数据了，再搞一个平行的"集合"纯属重复。
- 主题并入**标签** —— 标签本来就要打分、排序、限 5 个，再分一层 topics 只让界面更复杂。
  将来内容真变杂了，按标签频次派生 topics 也不迟，不必提前建模。

四条硬规则：

1. **同一个词不允许跨轴重复**。判定成 `docType=电子书` 就不会再把「电子书」当标签。
   现在的「学习资料 + #学习」就是这么坏掉的。
2. **文件夹优先**。文件夹名与路径是确定性信号（`L30_面向对象进阶/继承测试` → 标签 `继承`），
   权重最高（+10）。这条把「56/57 个 Java 文件靠关键词碰巧命中」变成「一定命中」。
3. **体裁只认结构，不认主题词**。沿用已有的 `_genreSignals` 思路并收紧：
   参考文献/致谢/本章/练习题/出版社/摘要/关键词/目录 这类标记**每个只计一次**，
   命中 ≥2 个 → 体裁定案；主题词再多也不能推翻体裁。
4. **主题词在大库里必然饱和**，所以按 **IDF 加权**：一个词在库里越常见越不值钱
   （「设计」「方案」在 60 份文档里 40 份都有 → 权重接近 0；「多态」只在 4 份里有 → 高分）。
   这一条直接消灭"泛词靠堆量赢"的问题，比现在的 `_ambiguousKeywords` 手工表更省事。

### 5.3 标签打分（可解释 + 上限）

```
score(tag) = Σ 来源权重，取前 5，且必须 ≥ 阈值 6
  目录命中          +10
  标题/文件名命中   +8
  正文命中 n 次     +min(6, 1.5·log2(n))，n ≥ 3 才计
  AI 提议（须引用原文片段）+6，且必须已存在于受控词表
  跨类别散布惩罚    ×0.5（同一词在多个类别都高频 → 是泛词）
```

每个标签存 `{ name, score, from: ['dir','title','body:12','ai'] }`，
UI 用现有的 `data-tip` 气泡解释「为什么有这个标签」——复核时不用猜。

标签分两类，一起存，来源标明：

- **自动推导**：文件夹/标题/正文证据算出来的，必须过阈值、最多 5 个，低分就不出现；
- **手动标记**：你自己加的（`#重要` `#待整理`），永远保留，不参与打分也不被自动清掉。

### 5.4 分类词表重做

现在 10 个类目是"体裁 + 主题 + 生活领域"的混合体，对这套语料没有区分力。改成分层词表：

### 5.5 复核工作流

- 置信度 < 阈值、或前两名主题分差 < 20% → `needsReview: true`。
- UI 加「待确认」筛选（复用现有徽章样式），支持**批量接受/改写**（已有 `/docs/batch` 与 `/tags/rename` 可以垫底）。
- `classify.evidence` 让复核界面能显示：`命中「继承测试」目录 + 标题「T7 继承」→ topics: 继承`。
- AI 只在**受控词表内**提议，且必须给出原文引用；API key 没配时整条链路自动跳过（现在就是这样，保持）。

## 五·五、存储范围：用「能力表」代替扩展名清单

**范围已定：纯文本资料。不做图片、音频、视频、压缩包、邮件与字幕。**
这个决定砍掉了整个媒体预览链路和配额问题 —— 所有格式都能抽正文、都能网页预览，
不存在「只能下载」的类别，`extract` / `preview` / `index` 三项能力退化成两档，
实现量比原方案少一半。

现在 `file-types.mjs` 的 `EXT_ALIASES` 只回答「能不能存」，
「能不能搜到正文」「能不能网页看」散在各处分支。改成每条登记能力，加格式只改一行：

```js
// _lib/file-types.mjs (v2)
'.pdf':  { type:'pdf',  extract:'pdf',   preview:'browser', index:'full', editable:false },
'.docx': { type:'docx', extract:'docx',  preview:'html',    index:'full', editable:false },
'.xlsx': { type:'xlsx', extract:'xlsx',  preview:'sheet',   index:'full', editable:false },
'.pptx': { type:'pptx', extract:'pptx',  preview:'html',    index:'full', editable:false },
'.md':   { type:'md',   extract:'plain', preview:'markdown',index:'full', editable:true },
'.txt':  { type:'txt',  extract:'plain', preview:'text',    index:'full', editable:true },
'.csv':  { type:'csv',  extract:'plain', preview:'sheet',   index:'full', editable:true },
'.java': { type:'code', extract:'plain', preview:'code',    index:'full', editable:true },
'.html': { type:'code', extract:'html',  preview:'code',    index:'full', editable:true },
'.doc':  { type:'doc-legacy', extract:null, preview:'none', index:'none', editable:false },
```

### 支持清单（最终）

| 类别 | 扩展名 | 网页上能做什么 |
|---|---|---|
| PDF | `.pdf` | 原生阅读、页内搜索、下载 |
| Word | `.docx` | 排版预览（网页视图）+ 正文可搜 + 下载 |
| Excel | `.xlsx` | 表格预览（合并单元格/列宽）+ 正文可搜 + 下载 |
| PPT | `.pptx` | 逐页预览 + 正文可搜 + 下载 |
| **Markdown** | `.md .markdown` | **渲染预览 + 网页内编辑 + 全文可搜**（见下一节） |
| 纯文本 | `.txt .csv` | 预览 + 网页内编辑 + 全文可搜 |
| 代码 | 现有全部（java/ts/py/go/rs/json/yaml/sql/html/css…） | 语法高亮预览 + 网页内编辑 + 全文可搜 |
| 旧格式 | `.doc .xls .ppt` | 只存与下载，**明确提示「另存为新格式后可搜索」** |

### 明确不做（这一版）

- 图片 / 音频 / 视频：**不做**。连带取消媒体配额、`<img>/<audio>/<video>` 预览、HEIC 转码、SVG 内联的 XSS 处理。
- `.eml`、`.srt/.vtt`、`.tsv/.log`：不做。
- `.epub`：不做（你之前明确排除过）。真需要时按能力表加一行即可，不用改 pipeline。
- 私钥与证书（`.pem/.key/.p12`）：继续**拒收**。这个库默认公开可见，不适合放。

压缩包不在上面这条清单里 —— 它**不作为存储对象，而是作为导入通道**，见下一节。

### Markdown 是这一版的重点（你说要 markdown）

已有：`.md` 能存、能渲染预览（marked）、能在网页里编辑、能抽正文进索引。
但只做到"能打开"。要做成真正能用的写作与笔记工具，还差这些：

1. **双栏实时预览**：左边写，右边同步渲染（现在只有预览/编辑切换）。
2. **工具栏 + 快捷键**：标题、粗斜体、列表、引用、代码块、表格、链接、待办；
   `Ctrl+B/I/K`、`Tab` 缩进、`Ctrl+S` 保存（配合已有的 `rev` 乐观锁）。
3. **网页内新建文档**：`POST /docs` 创建一篇空白 markdown，直接落在当前文件夹。
   —— 有了"自己建文件夹"，下一步必然是"往里写东西"，这是配套能力。
4. **YAML front matter 驱动元数据**：
   ```yaml
   ---
   title: 多态笔记
   tags: [面向对象, 多态]
   type: 笔记
   ---
   ```
   写入时解析成 `doc` 的 `title/tags/docType`，front matter 本身不参与正文索引。
   这让文档自己带元数据，也方便你用任何编辑器在本地写。
5. **内部双链**：`[[文档标题]]` 或相对路径链接 → 渲染成站内链接，反链面板列出「哪些文档提到我」。
   这是把「资料库」变成「个人 wiki」的关键一步，也是找资料最快的方式。
6. **目录（TOC）+ 标题锚点**：长文档侧边浮出目录。
7. **代码块**：语言标注 + highlight.js 高亮（依赖已有）+ 一键复制。
8. **GFM**：表格、任务列表、删除线、脚注。
9. **导出**：下载原文 `.md`；同时提供 `/file` 原始下载（已有）。

## 五·六、文件夹：从「路径推导」改成「第一类数据」

**现在**：文件夹是你上传时的相对路径 `上传/学习/L30_面向对象进阶/继承测试` 推导出来的
（`dirOf()`）。后果：不能建空文件夹、不能改名、不能移动、删除一个文件夹等于批量删文档。

**改成虚拟文件夹树**：

1. 新增 store `doc-folders`：`{ fid, name, parentFid, visibility, createdAt, order }`。
2. 文档新增 `fid`，`sourceKey` 继续保留（它是**同步身份**，不是组织方式）。
3. **上传整目录自动建树**：按相对路径逐级 `ensureFolder()`，同路径幂等 ——
   重复推同一个目录不会长出重复文件夹，「改的替换、增的加入」继续成立。
4. **手动操作**：新建 / 重命名 / 拖拽移动 / 多选批量移动 / 删除（子项进「回收站」，不直接销毁）。
   空文件夹立刻可见 —— 这正是你上次问「为什么我没看到文件夹」的另一半答案。
5. **移动文件夹 = 改一个 `parentFid`**（O(1)），不需要批量改所有文档路径 ——
   这是虚拟树相对真实路径最大的好处。
6. **可见性继承**：文件夹可设为 private，子文档与子文件夹继承。
   有效可见性 = 自己 public 且所有祖先都 public。
   存简历、合同、私人笔记时，「整个文件夹一设私有」必须是一步操作。
7. 同一父目录下重名 → 自动加后缀（`资料 (2)`），不报错。
8. `/manifest` 直接下发树结构，前端 sidebar 渲染，不再从路径拼字符串。

## 五·七、压缩包：只当「导入通道」，不当存储对象

丢一个 zip 进来 → 自动解开、逐个入库、按包内目录建文件夹。**压缩包本身不入库**（提取成功后丢弃原件），
理由：避免同一批内容存两遍；想拿回压缩包，「下载整个文件夹为 zip」随时能重新打。

### 流程

```
上传 .zip（分片，≤30MB）
   → POST /inbox/archive        解压 + 逐个写暂存区 + 建文件夹树
   → POST /inbox/ingest 循环    现有队列按批入库（每批 ≤3–10 份，避开 26 秒上限）
   → 返回报告：提取 47 份 · 入库 45 份 · 跳过 2 份（不支持 png×2）
```

复用现有两阶段（暂存 → 入库）架构，不新增调度器：解压是毫秒级操作，
真正的耗时在 PDF 抽取与索引，那部分已经由「按 id 点名 + 分批」解决。

### 关键设计

1. **`sourceKey = archive://{zip名}/{包内路径}`**。这是增量同步的关键：
   改了内容再丢同一个 zip 进来 → 改的替换、增的加入、包内已删的提示消失，与现在的目录同步语义完全一致。
2. **解压落到以压缩包命名的文件夹**（`书籍包.zip` → 文件夹 `书籍包/`），包内目录结构逐级保留。
3. **只支持 `.zip`**。`.7z/.rar` 线上解不了（没有纯 JS 实现；`node-7z` 要外部二进制，函数里没有）。
   遇到 `.7z/.rar` 直接拦下并提示：「请用 7-Zip 转成 zip，或解压后拖文件夹进来」。
4. **中文文件名必须处理 GBK**。Windows 打包的 zip 常用 GBK 编码且不带 UTF-8 标志位，
   按 UTF-8 解码会得到一堆乱码文件名。解法：检测到非法 UTF-8 序列时用 `TextDecoder('gbk')` 重解
   （需要完整 ICU，Netlify 的 Node 20 官方构建应该有，实施时本地与线上各验一次）。
5. **安全与限额**（zip 是唯一会被"解开"的输入，必须卡死）：
   | 限制 | 值 | 防的是什么 |
   |---|---|---|
   | 压缩包大小 | ≤ 30 MB | 云端内存 1024 MB，jszip 要整包在内存里 |
   | 解压后总量 | ≤ 300 MB | zip bomb |
   | 解压比 | ≤ 100:1 | zip bomb |
   | 条目数 | ≤ 500 | 函数时限与一次入库规模 |
   | 单个包内文件 | ≤ 100 MB | 与直传一致 |
   | 嵌套压缩包 | 不递归，报告提示 | 无限套娃 |
   | 路径穿越 | 拒绝含 `..`、绝对路径、盘符的条目 | zip slip |
   | 加密包 | 明确报错「不支持加密压缩包」 | 解不开还占位 |
6. **垃圾过滤**：`__MACOSX/`、`.DS_Store`、`Thumbs.db`、`desktop.ini`、`~$*` 直接丢弃不计数。
7. **不支持的包内类型**（图片/视频/音频/7z）→ 跳过并在报告里列出来，不静默。
8. **超过 30 MB 的包**：提示用本地脚本 `node scripts/ingest.mjs "<解压后的目录>"` ——
   本机解压后走目录入库，不受函数任何限额。这是能力边界，不是缺陷。

## 五·八、多文件下载：选中的东西打成一个 zip

同一个「打包」能力服务三处，只换输入：

| 入口 | 输入 | 产物 |
|---|---|---|
| 多选下载 | 勾选的 N 份文档 | `选中-2026-10-29.zip` |
| 下载整个文件夹 | 一个 `fid`（递归） | `文件夹名.zip` |
| 备份导出（P0） | 全库 | `资料库备份-2026-10-29.zip`（含 `manifest.json` 与每份的 text） |

### 两种实现，按体积选

1. **浏览器打包（默认）**——前端并发拉 `/docs/{id}/file`，用 JSZip 在本地打包下载。
   - 优点：不碰函数限额（6 MB 请求体 / 26 秒 / 内存），选中多少都行，服务器零成本。
   - 约束：纯文本资料量级完全够用（几百份也就几十 MB）；断网会中断。
2. **服务端打包（大选择时）**——`POST /download/bundle { ids | fid }` 生成 zip 存进 Blobs，
   返回一次性下载链接，客户端再拉。用于「整个文件夹 200 份、80 MB」这种。
   - 受 26 秒与内存限制，超了就退化成"分批 + 客户端合并"或提示用本地脚本。

zip 内保留完整路径（文件夹层级），备份导出另加 `manifest.json`（标题/标签/分类/来源/时间），
这样解压出来的东西自己说得清是什么。

## 七、单一写入门闸

所有写操作（上传入库、本地脚本、批量打标、内容编辑、删除、恢复、复核）都走同一个函数：

```js
// _lib/doc-write.mjs
await writeDoc({ op: 'upsert' | 'patch' | 'delete' | 'restore', sourceKey | docId, patch, ifRev })
// 1) 取旧 doc → normalizeDoc → 校验
// 2) 写真相层（meta/text/file）
// 3) 更新派生层 manifest（含 rev）
// 4) 索引增量（失败 → doc.index.pending = true，不影响成功返回）
// 5) 返回 { doc, warnings }
```

配套：

- **幂等键** `sourceKey + contentHash`：同一文件重复推 = no-op，不再产生重复文档。
- **并发**：`ifRev` 不匹配 → 409（沿用现有语义）。批量操作走一次读、一次写（现成 `applyDocChangesBulk` 的思路）。
- **`index.pending` 自愈**：列表显示「索引待更新」，`/index/repair` 或后台扫描补上；
  搜索遇到 pending 文档时退化为扫 `meta` 前缀匹配，**绝不静默丢失**。

## 十一、明确不做（及理由）

- **不换数据库**：SQLite/Turso/Supabase 不能解决上面任何一个缺陷，现在的瓶颈是模型与一致性，不是存储。
  但 `writeDoc` 会做成唯一入口，将来要换存储**只改一个文件**。
- **不拆函数**：按端点拆成十几个函数只会增加冷启动与部署面；单路由现在是对的。
- **不重做 UI**：纸本主题与 DOM 契约保留，只**增**筛选维度。
- **不把 AI 打标做成主链路**：key 未验证前，AI 永远是"受控词表内的建议者"，规则先保证可用。
- **不做多端协同编辑**：个人库不需要，`rev` 乐观锁足够。
